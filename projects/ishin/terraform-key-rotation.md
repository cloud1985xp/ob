ishin-tw-prod and ishin-tw-dev are completely mirrored in the service accounts.

## Key and Key Group

For each service account has 2 keys created: key alpha and key beta.
For example, for the service account of redash@production, it will have 2 keys generated by terraform: `redash_production_alpha` and `redash_production_beta`. And categorized them as key group: alpha and beta

The all keys in the same group have the same expiration, 2 groups used different expiration cycle by 45 days shifted.

### Key Rotation and Key Group Rotation

The keys are rotated every 90 days defined by terraform

Those 2 rotation cycles had 45 day shifted, which means they have another 45 days overlapped. For each group they have 45days as core (activate) period, another 45days as buffer period.


From service side, they are using the key group within active period, and when the expiration is closing, it will rotate to another key group. That's `KeyGroup rotation`

On the other words, `Key group rotation` should always happens before `key rotation`.

| Key Rotation                          | KeyGroup Rotation                                                                                                    |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Delete Old and Create New Keys on GCP | Switch current group flag and fetch new keys from terraform then update them to everywhere using by related services |

### Current Key Group

We need a flag to represent what's the key group current using. It's stored in SSM by each project. With parameter name as:

`/common/ishin-jenkins/key_rotation/${PROJECT}/CURRENT_KEY_GROUP`


## Process

We can treat the process as 2 tracks

Track A: Key Rotation
Processed by terraform, it runs terraform apply everyday forwarding to desired state
Which means when key rotation expired, it will auto delete old key and create new one

Track B: Key Group Rotation
A process which run everyday to detect if key rotation is closing. If yes, perform key group rotation to:

- Update flag of current group to another key group
- Update all service to use key of current key group

## 3 Pipelines

### Terraform Apply

It daily runs terraform apply command to ensure the state of GCP resource is full-sync with terraform.

That's how the key rotation actually performed. When the key rotation expires, it deleted the expired one and generate new key

### GCP Key Group Attempt Rotation 
Another pipeline runs daily. It tries to detect if the key expiration is closing (expired after N day). If yes, which means the current key group has entered buffer period and required switching. Then it performs key rotation by:

- Update the flag of current group to another key group on SSM
- And run another(the next one) pipeline to update the keys of related service to use the new key


### GCP Key Group Refresh
It's an individual pipeline which perform update of related services to use GCP keys of specified key group. Depends on the service it has different way to update key. For example

For the service retrieved GCP key from SSM, it run AWS cli to update the specific parameters on SSM
For Redash, it calls redash API to upload the new key
