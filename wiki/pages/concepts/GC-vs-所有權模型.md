# GC vs 所有權模型的記憶體管理

[[Discord]] 從 Go 遷移到 Rust 的案例揭示了垃圾回收（GC）與所有權模型在高效能場景下的根本差異。

## Go 的 GC 問題

**症狀**：大型 LRU 快取的服務，每 2 分鐘出現延遲峰值。

**根本原因**：
1. Go 強制每 2 分鐘執行一次 GC（無論記憶體使用如何）
2. GC 需要掃描**整個 LRU 快取**的所有物件，確認是否有引用
3. 快取越大 → GC 掃描時間越長 → 延遲峰值越嚴重

**嘗試解法均失敗**：
- 調整 GC 百分比：分配速率太低，不觸發更頻繁的 GC
- 縮小 LRU：降低 GC 影響，但增加快取未命中率（兩害取其輕）

## Rust 的所有權模型

- **沒有 GC**：不需要掃描，不需要 runtime 判斷哪些記憶體可回收
- **所有權追蹤**：編譯器在**編譯時**確保記憶體安全規則
- **即時釋放**：當物件離開作用域或從 LRU 淘汰時，**立即**釋放記憶體

**結果**：Discord 的 Rust 版本沒有延遲峰值，而且延遲降到微秒級別。

## 效能對比（Discord Read States 服務）

| 指標 | Go（調整後） | Rust（基礎版） | Rust（最佳化後） |
|------|------------|--------------|----------------|
| 延遲 | 毫秒，每 2 分鐘峰值 | 毫秒，無峰值 | **微秒** |
| CPU | 基準 | 相當 | 更低 |
| 記憶體 | 基準 | 相當 | 更低 |

## 關鍵洞察

> GC 的問題不只是「停頓」，更是它需要掃描**所有活躍物件**來確定什麼是垃圾。
> 當快取中有數千萬個物件時，這個掃描本身就是效能殺手。

## 何時選擇 Rust vs Go

| 場景 | 建議 |
|------|------|
| 高吞吐量、低延遲（微秒級）、大型記憶體結構 | Rust |
| 開發速度優先、延遲容忍度較高 | Go |
| 已有 Go 代碼且效能尚可 | 維持 Go，不必重寫 |
