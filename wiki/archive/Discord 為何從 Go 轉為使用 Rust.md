Rust 在多個領域逐漸成為一流的程式設計語言。Discord 在客戶端和伺服端使用 Rust 都已收穫不錯的成效。例如，我們在客戶端使用 Rust 處理好友直播的視訊編碼管道，而在伺服端則用來處理 [Elixir NIF](https://blog.discordapp.com/using-rust-to-scale-elixir-for-11-million-concurrent-users-c6f19fc029d3) 。我們最近將一項服務的實作語言從 Go 切換到 Rust，顯著提升了其效能。這篇文章將解釋為何我們決定重新實作這項服務、如何完成，以及最終的效能改善成果。

### Read States 服務

Discord 向來著重產品，因此我們先來談談產品背景。我們從 Go 切換到 Rust 的是「Read States」服務，唯一的功能就是追蹤您閱讀過的頻道和訊息。當您每次連接至 Discord、傳送和閱讀訊息時，都會存取 Read States。簡而言之，Read States 是執行頻率很高的重要服務。我們希望 Discord 用起來隨時感覺快速順暢，因此必須確保 Read States 的速度夠快。

在 Go 語言實作中，Read States 服務並不符合其產品需求。該服務大多數時候速度很快，但每隔幾分鐘，延遲就會突然提高，影響到使用者體驗。經過調查，我們確定這些延遲高峰的起因是 Go 的核心功能：記憶體模組和垃圾回收器（GC）。

### 為何 Go 未能達到效能目標

如要解釋為何 Go 語言沒有達到我們的效能目標，首先必須討論此服務的資料結構、規模、存取模式和架構。

我們將用來儲存讀取狀態資訊的資料結構簡單稱為「Read State」。Discord 上有數十億個 Read State，每位使用者的每個頻道都有一個 Read State，每個 Read State 都有多個需要經過原子性更新的計數器，且經常會重置為 0。例如，其中一個計數器是計算您在頻道被 @ 提及多少次。

為了快速進行原子計數器更新，每個 Read States 伺服器都有一個「最近最少使用（LRU）」的 Read States 快取。每個快取中有數百萬名使用者，數千萬個 Read States，且每秒有數十萬次快取更新。

為了實現持久性，我們使用 Cassandra 資料庫叢集支援快取。淘汰快取鍵值時，我們會將您的 Read States 提交到資料庫。每有一個 Read State 更新時，我們也會安排在 30 秒後進行資料庫提交，而每秒有數萬次資料庫寫入。

在下圖中，可以看到 Go 服務中單一峰值採樣時間段內的回應時間和系統 CPU。¹ 可以注意到，大約每 2 分鐘，延遲和 CPU 用量就會突然大幅提高。

### 為什麼每 2 分鐘會大幅提高？

在 Go 中，當淘汰快取鍵值時，記憶體不會立即釋放。相反地，垃圾回收器會不定期運行，尋找任何沒有引用的記憶體並進行釋放。換句話說，當記憶體不再使用時並不會立即釋放，而是會暫時保留一段時間，直到經過垃圾回收器確定後，才會進行釋放。垃圾回收期間，Go 必須執行大量工作來確定哪些記憶體是在空閒狀態，而這會減慢程式速度。

延遲提高的問題看似是受到垃圾回收效能的影響，但我們編寫的 Go 程式碼已經達到很高的效率，並且幾乎沒有分配。我們並沒有產生很多垃圾。

在深入研究 Go 的原始碼後，我們發現 Go [至少每 2 分鐘](https://github.com/golang/go/blob/895b7c85addfffe19b66d8ca71c31799d6e55990/src/runtime/proc.go#L4481-L4486) 就會強制執行一次垃圾回收。這也代表，如果在 2 分鐘內未執行垃圾回收，無論堆記憶體的增長情況如何，Go 仍然會強制執行垃圾回收。

我們以為可以透過調整垃圾回收器的運行頻率，進而防止突發的高延遲，於是在服務中實作了一個端點，以便快速更改垃圾回收器的 [GC 百分比](https://golang.org/pkg/runtime/debug/#SetGCPercent) 。可惜無論我們如何設置 GC 百分比，情況都沒有改變。究竟是怎麼回事呢？原來是我們分配記憶體的速度太慢，無法強制提高垃圾回收的運行頻率。

我們持續調查後發現，這些延遲峰值之所以如此嚴重，不是因為有大量待釋放的記憶體，而是因為垃圾回收器需要掃描整個 LRU 快取，才能確定記憶體是否真的沒有任何引用。因此我們推測，只要使用較小的 LRU 快取，垃圾回收器需要掃描的內容就會減少，速度也會變快。我們為服務新增了另一個設定來調整 LRU 快取的大小，並將架構更改為每個伺服器擁有多個分區的 LRU 快取。

我們的推測是是的。隨著 LRU 快取變小，垃圾回收的延遲峰值也縮小了。

然而，縮小 LRU 快取的代價是多數存取的延遲時間提高。這是因為快取變小後，使用者的 Read State 出現在快取中的機率便會降低，如果在快取中找不到，就必須載入資料庫。

我們針對不同快取容量進行大量負載測試後，找到了一個看似不錯的設定。雖然稱不上完美，但也還算令人滿意。由於還有更緊急的事項需要處理，因此我們便讓服務以這種方式運行了一段時間。

那段期間裡，我們發現 Rust 在 Discord 其他部分的成效越來越好，因此大家決定建立所需的框架和程式庫，打造完全使用 Rust 語言開發的新服務。這項服務非常適合移植到 Rust，因為它規模小又獨立，而我們也希望 Rust 能夠解決突發延遲的問題，於是我們著手將 Read States 移植到 Rust，希望能驗證 Rust 作為服務語言的功效，並且改善使用者體驗。²

### Rust 內的記憶體管理

> Rust 的速度極快且記憶體效率很高。它 **沒有執行階段或垃圾回收器** ，可以為效能關鍵型服務提供動力，在嵌入式裝置上運行，還能輕鬆與其他語言整合。³

Rust 並沒有垃圾回收機制，因此我們認為它不會出現和 Go 相同的突發延遲狀況。

Rust 採用了一種相對獨特的記憶體管理方法，其中包含了記憶體「所有權」的概念。基本上，Rust 會追蹤誰可以讀取和寫入記憶體。它知道程式何時正在使用記憶體，並在不再需要時立即進行釋放。它會在編譯時強制執行記憶體規則，使得執行階段幾乎不可能出現記憶體錯誤。⁴ 沒必要手動追蹤記憶體，編譯器會負責處理。

因此，在 Rust 版本的 Read States 服務中，當使用者的 Read State 從 LRU 快取中淘汰時，就會立即從記憶體中釋放。Read State 的記憶體不會暫時保留，等待垃圾回收器進行回收。Rust 會知道這些記憶體沒有在使用，並立即進行釋放，不需要執行階段程序來判斷相關記憶體是否應該釋放。

### 非同步 Rust

不過，Rust 生態系統存在一個問題。當我們重新實作這項服務時，Rust 的穩定版尚未充分支援非同步 Rust。對於網路服務而言，支援非同步程式設計是一項必要條件。雖然有少數社群程式庫能夠支援非同步 Rust，但它們需要大量的處理步驟，而且錯誤訊息非常難以理解。

幸運的是，Rust 團隊非常努力地讓非同步程式設計變得簡單，而且也能使其在 Rust 不穩定的夜間頻道中使用。

Discord 向來勇於使用有前景的新技術。例如，我們是在早期便採用 Elixir、React、React Native 和 Scylla 的公司。如果某項技術很有前景並能帶來優勢，我們並不介意處理尖端技術中難免會出現的困難和不穩定。這也是為什麼我們能在不到 50 名工程師的情況下，迅速達到超過 2.5 億名使用者。

使用 Rust 夜間版本中新的非同步功能是我們願意採用有前景的新興技術的另一個例子。作為一個工程團隊，我們認為 Rust 夜間版本值得使用，並且致力於在夜間版本上運行，直到穩定版完全支援非同步。我們一起解決了在此過程中遇到的問題，而目前 Rust 穩定版已支援非同步 Rust。⁵ 這場賭注已經得到了回報。

### 實作、負載測試和啟用

實際的重寫過程相對簡單。我們從粗略的轉譯開始，然後在合適的地方進行精簡。例如，Rust 擁有出色的類型系統，並且廣泛支持泛型，因此我們可以捨棄部分為了因應缺少泛型而生的 Go 程式碼。此外，Rust 的記憶體模型能夠在多執行緒間處理記憶體安全，因此我們可以捨棄一些在 Go 中所需的手動跨 Goroutine 記憶體保護機制。

我們開始執行負載測試後，立刻就對結果很滿意。Rust 版本的延遲狀況與 Go 一樣優秀，而且 **沒有延遲突然飆升的狀況！**

值得注意的是，我們在編寫 Rust 版本時只進行了非常基本的最佳化。 **即便如此，Rust 還是能夠超越經過大量人工調整的 Go 版本。** 這充分證明了與需要深入調整的 Go 相比，使用 Rust 編寫高有效率的程式是件多麼容易的事。

不過，只是達到與 Go 相同的效能並不足以令我們滿意。經過一些分析和效能最佳化後， **新版本在每一項效能指標上都超越了 Go** 。Rust 版本的延遲、CPU 和記憶體表現都更加出色。

Rust 效能最佳化包含：

1. 將 LRU 快取中的 HashMap 更改為 BTreeMap，使記憶體使用最佳化。
2. 將最初的指標庫替換為使用現代的 Rust 並行性指標庫。
3. 減少記憶體副本數量。

我們在感到滿意後決定推出這項服務。

由於已進行過負載測試，我們的推出過程相當順利。我們將發行版本部署到單一的 Canary 節點，發現了一些遺漏的邊緣案例並進行了修正。不久之後，便套用到整個集群。

### 提升快取容量

服務成功運行幾天後，我們決定是時候重新提升 LRU 快取的容量了。如前所述，在 Go 版本中，提升 LRU 快取的上限會導致垃圾回收時間延長。由於我們不再需要處理垃圾回收問題，因此我們認為可以提升快取上限，獲得更好的效能。我們增加了伺服器的記憶體容量，並對資料結構進行了最佳化、進一步減少記憶體使用量（單純為了好玩），同時將快取容量提升到 800 萬個 Read States。

### 不斷演進的生態系統

最後，Rust 另一個超棒的優點在於擁有快速發展的生態系統。最近，tokio（我們使用的非同步執行階段）推出了 0.2 版本。我們完成升級，藉此免費使 CPU 的效能提升。從下圖中可以看到，CPU 使用率從 16 日左右開始持續降低。

### 結語

目前，Discord 在其軟體堆疊架構的許多地方都使用了 Rust。我們用它來處理遊戲 SDK、好友直播的視訊捕捉和編碼、 [Elixir NIF](https://blog.discordapp.com/using-rust-to-scale-elixir-for-11-million-concurrent-users-c6f19fc029d3) ，以及不同後端服務等等。

當我們開始進行一個新的專案或軟體元件時，就會考慮使用 Rust。當然，我們只會在合適的地方使用。

除了效能以外，Rust 對於工程團隊而言還有許多優勢。舉例來說，當產品需求發生變化或我們對該語言有新的理解時，Rust 的類型安全性和借用檢查器會使程式碼重構變得非常容易。此外，Rust 的生態系統和工具也非常出色，並且擁有相當大的發展動力。

如果您願意看到這裡，那麼您可能剛對 Rust 產生了興趣，或是已經對它感興趣一陣子了。若您希望在專業環境下使用 Rust 解決有趣的問題，可以考慮來 Discord 工作。

另外，還有一個有趣的冷知識：Rust 團隊會使用 Discord 來協調工作。我們還有一個非常實用的 Rust 社群伺服器，您可以偶爾看到我們在那裡聊天。 [請點擊此處查看。](https://discord.gg/tcbkpyQ)
