# SRE Simulator Game

Created: 2024年6月29日 上午10:04

這是一個用 Elixir + Phoenix + Liveview 開發的一個網頁遊戲，前端的部分使用 esbuild 來打包 javascript 實作，並用 TailwindCSS v3 來製作基本的 UI 介面，更多進一步的畫面如動畫、特效等暫時先不定義，我們一步一步來漸漸建構它

以下為遊戲的設計概念與玩法架構

首先假設 TICK RATE 為 30，即 SERVER 每 30ms 向 CLIENT 端發送一次事件，稱為時間軸的推進

遊戲的類型為經營生產模擬，主題為 IT公司的工程開發團隊，負責開發各種網路應用程式產品，並上線營運產品來達成經營目標，

開發線上產品例如：

- 品牌形象網站
- 社群直播服務
- 電商平台
- 手機遊戲服務
- 大型售票系統

等等

上線營運面對各種事件例如：

- 累積活躍用戶
- 達到同時在線人數門檻
- 達成營收目標

等等

玩家扮演一個 IT公司的 CTO 帶領的IT工程團隊

工程團隊可以有很多成員，為遊戲中主要行動的角色，類似手機遊戲中玩家持的卡牌角色

每名角色會有多項數值設計：

五項主要屬性能力，簡稱主屬：

- 伺服端程式開發：如 Server API, Web Application Backend)
- 客戶端程式開發：包括 Mobile App., Web 前端)
- 用戶介面設計：包括UI、UX、美術設計)
- 營運能力：雲端 Infrastructure 建置管理，產品持續整合(CI/CD)，SRE 等
- 產品：產品規劃設計、包裝行銷等

(可以類比一般手遊角色的物理攻擊、魔法攻擊、防禦、敏捷等屬性)

COST：代表角色出戰的成本

職業：不同的職業對應角色擅長的主屬，以及成長的補正方向也不同

稀有度：愈稀有的角色基本主屬較高，COST通常也較高，而成長曲線也不同

技能：角色可以多項技能，可能包括主動技、被動技、連繫技等，之後會補充設計

玩家可以持有多個工程師在他的角色池中，依不同的關卡需求派出不同的角色組合闖關

遊戲的 IN-GAME 關卡的主要概念與架構

每個關卡都會分兩個階段，「開發階段」與「營運階段」

開發階段會設定一個開發的產品目標，例如一個線上服務、一個線上遊戲伺服器等等，稱之為目標產品

目標產品會帶有一些屬性參數，會做為營運階段的指標，類似於 SRE 中的 SLI

例如「服務穩定度」、「產品效能」、「回應速度」、「使用者體驗」、「容錯能力」等等，稱為產品能力值

玩家的目標是在「開發階段」透過一輪一輪的生產，完成一些生產項目，每個生產項目會提供產品能力，累積這些產品能力值的數值之後，進到「營運階段」

在營運階段時，此時會模擬這個服務的伺服器在單位時間內持續受到使用者訪問、呼叫 API、瀏覽操作等行為，持續它造成負荷，經由與產品能力值和一些隨機因子的運算，來模擬一段時間序列下每個 TICK 營運指標，例如「CPU 服荷」、「每分鐘要求數(RPM)」、「回應時間」、「錯誤率」、「流量」、「玩家行為到達率」、「單位時間活躍用戶數」、「ARPU(Average Revenue Per User」等數據指標

最後用這些指標，評比是否有達成關卡所設定的目標條件

例如

- 單位時間內營收達到 $100000
- 平均 CPU Utilization < 60% 且 Rponse Time < 300ms

以下說明關卡進行、開發階段和營運階段的架構與流程

## 進入關卡

在進入關卡一開始，玩家依關卡的描述先挑選要出場的角色(工程師)，並且將出場角色分成數個小隊

關卡描述會介紹關卡要開發的產品，以及之後營運的目標，並且會提示可能偏重的生產項目和部分生預覽，玩家藉此來判斷適合出場的角色與分隊方式

關卡資訊還包括以下的關卡設定條件：

- 組隊數的上、下限，範圍是 2~5
- 有幾輪的開發生產循環，稱為 Sprint，範圍 2~6
- 出戰的總 COST 上限

## 開發階段

在開發階段，會分成多個 SPRINT 進行，

- SPRINT 的總數依關卡而定
- 每個 SPRINT 會有固定的回合數，例如 20 個回合，
    - 也對應到這個關卡的時間長度，假設在遊戲速度1倍數進行下一個回合是 100個TICK = 3秒， 那這一個 Sprint 跑完基本需要 60 秒
    - 可以透過設定遊戲速度來加快節湊，但關卡的總回合數不會被影響
- 每個 SPRINT 會被設定有多個生產開發項目，即為 TICKET，系統會設定多個 Ticket 給每個 Sprint，在進行過程中從 TICKET 池中隨機挑選項目出來

玩家的挑選的工程師，會被分成數個小隊，每個小隊的目標就是要在每個 SPRINT 中完成被分派的 TICKET

每個 TICKET 被完成後，會增加目標產品的「產品能力值」，

透過完成 TICKET 就會讓目標物獲得這些獎勵，累積提升對應的產品能力值

每個 TICKET 都會從五項主屬中挑中2-3項，並設定目標值，來代表這張 TICKET 被完成的目標參數

例如 伺服端=70,  設計=25, 產品=24

而每個小隊會依工程師角色的組成，總計出該小隊的每單位時間(回合)的生產力

例如 伺服端=12, 設計=4, 產品=9

所以就需要花 6 個回合才能完成這個 TICKET

每個 SPRINT 都依以下流程循環：

- PLAN：決定這輪開發的 Tickets，並分派 Ticket 給各小隊
- ACTION：進行開發，遊戲時間軸會進行，開始推進回合數累績生產
- REVIEW：回顧各小隊的生產結果，並確認再進行下一個 Sprint，直到完成關卡設定的 Sprint 數

### PLAN

此時遊戲時間軸是停止的

- 先進行分組，玩家可將出場的工程師分成數個小隊
- 系統從資料庫中抽出多個 TICKET(每個SPRINT的 TICKET 池總數依關卡設計而定)
- 玩家將 TICKET 分派給各小隊，分派的方式：
    - 每一輪出現三個 TICKET，玩家可任意選擇這三張要分配給任一小隊
    - 也可以略過目前這輪，再進到下一輪出現再三個 TICKET
    - 直到
        - 玩家選擇結束
        - 所有小隊的負荷已滿
        - 沒有 TICKET 可以選

### ACTION

此時遊戲時間中開始運作，依 TICK RATE 進行回合的計算，更新狀態

SERVER 在每回合中計算

- 每個小隊正在處理的 TICKET，累計小隊產出的各屬性生產力
- 每個處理中的 TICKET 的進度，即主屬目標值的累積進度，是否達標

有關時間軸與回合

時間軸是代表 SERVER 定期發送事件到 CLIENT(依TICK長度)，來維持對 CLIENT 端的狀態更新

而每個回合的長度是數個 TICK，ACTION 階段的生產行為大多是基於回合，也就是一個回合才統計一次生產進度，不過有些狀態則是基於 TICK 持續更新的

ACTION 階段時間會持續推進，但玩家可以按下暫停鍵來暫停時間軸

有關發言系統

在 ACTION 階段，小隊的角色會隨機或條件觸發一些發言，原則上不影響遊戲進行

只是一些角色的小對話或murmur來增添趣味效果，發言的台詞依角色設定會有各自的文本庫設計

有關主動計系統

每位成員都會有 1~2 主動技，施放主動技必須消耗 Action Point(AP)

每個主動技需要的 AP 不同，會需要 1~3 點AP，

在 ACTION 階段，而每個小隊會有 Action Point (AP) 計量用來施放主動技

可施放的主動技就是成員擁有的技能

Sprint 一開始預設每個小隊都有1點AP，每當完成一張 Ticket，AP點數就增加一點，最多累計5點

主動技可以為小隊帶來效果，一個主動技可能有多個效果，可能同時包含增益和減益的效果

例如：增加 3點設計能力、專案能力 -50% 等

效果會有生效的對象範圍，例如整個小隊，或是指定特定成員

效果會有生效的時間區間，例如 3回合，或是永久

只要 AP點數夠，隨時都可以發動主動技，但主動技發動後，會進入冷卻時間，表示該技能不能再被使用，直到冷卻時間結束

除了主屬性生產力，每位成員有體力與意志力的，一開始都是 100

隨著 SPRINT的進行，每回合體力與意志力會減少

當體力減為零，該成員會完全沒有生產力

當意志力減少，該成員的生產力也會下降，會設計公式來計算不同的意志力對生產力的影響

每回合體力的減少量是經過計算的，主要是看當下進行的 Ticket 與成員本身職業擅長的屬性是否相符，愈相符體力減少愈多

每回合意志力的減少量也是經過計算，主要是看當下進行的 Ticket 與成員本身職業擅長的屬性是否相符，愈相符意志力減少的愈少

當小隊每回合產生的累積生產力，達到 Ticket 所需的條件值後，該 Ticket 會從開發中(DOING) 進到下一個狀態 REVIEW

REVIEW 會有一個固定的回合長度，例如2回合，經過2回合後，該 Ticket 會從 REVIEW 狀態進到下一個狀態：TESTING

TESTING 一樣會經過固定的回合長度，例如3回合，經過3回合後，該TICKET就會變成完成(DONE) 的狀態

當TICKET 從 DOING 進到 REVIEW 的狀態時，該小隊的所有成員就會進到休息

休息時就會回復一定額度的體力

休息結束，小隊會開始繼續下一個 Ticket (無論前一個 TICKET 是否仍在 REVIEW OR TESTING)

有一些技能的效果是恢復體力或意志力

小隊也可以透過發動技能來恢復體力或意志力，

這類型的技能是立即生效，所以也沒有持續多少回合的設定

當TICKET進到完成狀態，會將該 TICKET 所設定的獎勵值加到目標生產物上

各小隊持續 ticket 的生產循環，直到排定的所有 ticket 都被完成

直到 ACTION 階段的總時間長度結束

若所有小隊的 ticket 都完成了，sprint 也會提前結束

進入 Sprint 的 Review 階段

### REVIEW

Sprint 進到 REVIEW 時時間軸停止

會列出每個小隊完成的 TICKET ，以及統計得到的獎勵值

玩家確認後，

此時會跳出 Sprint Bonus 的選單

選單會提供三種 Bonus，玩家只能選擇其中一種

Bonus 也是會提供各種增益或減益的效果，會從下一個 Sprint 開始產生影響

(如果當下是最後一個 Sprint，則不會出現 Bonus 選擇)

玩家選擇好該次的 Sprint Bonus 後，確認按下一步再開始下一個 SPRINT 循環，一樣從 Plan 開始

如此重複 SPRINT 直到關卡設定的 SPRINT 次數都結束，進入到上線營運階段

## 營運階段

### 機制設計

前面的開發階段會為生產出來的「目標產品」累計產品的能力值

產品能力值包括(與對應 TICKET 的主要生產屬性)

- Performance：應用程式的效能品質，1)後端、2)客戶端、3)營運
- Availibility：系統可用性：1)客戶端、2)後端 3) 營運
- Stability：系統穩定度 1)營運、2)後端
- Scalibility：系統可擴張性 1)營運、2)後端
- User Arrival Rate：用戶到達率 1)設計、2)產品、3)客戶端
- Pay Rate：用戶付款率  1) 產品、2)設計、3)客戶端
- ARPU：單位用戶付款額 1)產品、2)設計

除了上述的產品能力值，營運階段還有幾個重要的屬性

首先是：

- Server Cost
- Server Scale

關卡會設定每單位 SCALE 每回合的 所要花費的 SERVER COST，以及關卡基本的 Scale 與起始 COST

Scale 會影響後續在計算各項目標指標，例如 SCALE 增加，Performance 會提升等等

但 Scale 若增加，就會連帶增加每回合的 SERVER COST

玩家可以透過技能、道具或事件等等，來影響 SERVER 的 SCALE 與 COST。

還有 SNS 滿意度

產品的表現會影響SNS的滿意度，SNS滿意度有可能會影響UAT, Pay Rate

並可能會觸發一些隨機事件

### 營運模擬

營運階段會依關卡的設定，開始對產品進行營運模擬

在營運階段我們一樣引入回合的概念，只是預設1TICK(30ms) = 一回合

關卡會設定這次的營運時間長度，例如 500 回合

每個關卡會設定不同的時間軸走向，主要是

- 流量分佈狀況
- 其他事件

流量分佈是營運階段玩家要面對的挑戰

指的是設定好在每回合使用者們對這個產品服務帶來的流量，簡稱RPT(Request per turn)（有點類似塔防受到的敵人攻擊）

關卡可以在流量分佈上設定一些高峰期

例如會在 T1、T2、T3 三個時間點發生P1、P2、P3

每個回合 SERVER 會將目標產品的各項能力數值，結合公式來計算每回合流量創造出來的各項數據

例如

CPU 負荷：依 Performance, Stability, 

DB 負荷：依 Scalibility, 

Latency：依 Performance, UI/UX

Active User：UI/UX, UAT

Revenue：依 UAT, Pay Rate, ARPU

Server Cost：Performance, Scale, 

詳細的公式需考慮平衡與合理性，之後再詳細設計

然後將當前的各項指標數據傳給 CLIENT 更新畫面狀態

CLIENT 端收到 SERVER 更新狀態，持續更新畫面

畫面上會呈現像是 SERVER 監控的儀表面，以圖形的方式持續更新各項指標的狀態

例如 Datadog, Cloudwatch Dashboard

勝利條件

勝利條件依關卡設定，可能會有複數的目標指標，例如

- AU 總計 > 10000 且 SERVER COST < 100
- REVENUE > 500000 且 平均 Latency < 0.8

失敗條件

- 關卡結束，未達成目標即為失敗
- 關卡過程中，產品下線長達 X 時間長度(依關卡設定) 或下線達 N 次
    - 產品下線可能是因為負載過高
    - 但也有技能可以讓產品可以超載運行

### 卡牌/道具/技能

預計還會設計一套卡牌/道具機制，在營運階段流量不斷湧入時，玩家可以視情況打出一些卡牌來應對狀況，或應付一些隨機事件，例如

- 減少 CPU 負荷 10回合
- 降低 Cost per scale 10 回合
- 提高 SNS 滿意度 5回合
- 提升 AU 5%

等等

遊戲流程

## IN-Game

分成開發階段與營運階段

- 開發階段就像是跑 sprint，在指定 sprint 內完成目標(解票)，打造好應用程式和基礎建設
- 營運階段就是系統上線後，開始有大量流量通入系統

### 開發階段

對應不同的關卡，需要開發不同的部件(service)

玩家要先依不同部件去設定小隊(SQUAD)成員

每個部件會限制

- 可以分配的組員 COST
- 需要達能力門檻(類似人龍一番經營)

每個 SPRINT 出現數個部件，讓玩家選擇要解哪個部件(票)

不同票完成會得到不同的獎勵/增益 → 最終產品的強化/能力

EX: 得到自動擴張、水平擴張架構、得到快取提升回應速度、強化 UI 提升轉換率

關卡會設定「開發週期」的長度: EX 4 個SPRINT

每個 SPRINT，各 SQUAD/部件

- 依小隊成員的能力值與隨機數值，推進部件的完成度
- 可發生隨機事件影響產出

開發週期結束後進入上線營運模式

= 產品上線迎單，外部使用者湧入

依最終目標來計算是否達成營運目標

### 營運階段

依關卡不同有不同的營運目標(關卡類期，像鬥陣推圖佔點、nikke有守城、殲滅等)

SPRINT 中間調整 SQUAD 人員配置

但會有額外成本/懲罰  - 有些TL可有特別技能應對
